# ثبت اطلاعات کل

سامانه ثبت اطلاعات داروخانه، پزشک، سفارشات و رصد تردد نمایندگان علمی.
Next.js 16 (App Router) + PostgreSQL (Drizzle ORM) + PWA (قابل نصب روی ویندوز، اندروید و iOS).

## دسترسی پیش‌فرض

| نقش | نام کاربری | رمز عبور | شماره همراه ورود |
| --- | --- | --- | --- |
| مدیر | `admin` | `admin1234` | `09120000000` |
| نماینده نمونه | `rep1` | `rep1234` | `09121111111` |

> با متغیرهای محیطی `ADMIN_PASSWORD` و `ADMIN_PHONE` می‌توانید مقدار اولیه مدیر را تغییر دهید
> (فقط در اولین اجرای دیتابیس خالی اعمال می‌شود). بعد از ورود، از مسیر «نمایندگان و دسترسی» رمز را عوض کنید.

## اجرای محلی (VS Code)

```bash
npm install
# فایل .env
# DATABASE_URL=postgresql://user:pass@host/db?sslmode=require
npm run dev
```

جدول‌ها در اولین اجرا **به صورت خودکار** ساخته می‌شوند (نیازی به اجرای migration نیست).

## استقرار روی Render + Neon

### چرا خطای «Could not find a production build» می‌گیرید؟

در لاگ Render فقط این خط دیده می‌شود:

```
==> Running 'npm start'
```

و **هیچ خطی از `npm run build` وجود ندارد** → یعنی فیلد **Build Command** سرویس شما خالی است.
`next start` فقط سرور را اجرا می‌کند و خودش بیلد نمی‌سازد، به همین دلیل پوشه‌ی `.next` وجود ندارد.

### راه‌حل قطعی (۲ دقیقه)

Render → سرویس شما → **Settings** → بخش **Build & Deploy**:

| فیلد | مقدار درست |
| --- | --- |
| Root Directory | خالی (اگر پروژه در ریشه‌ی ریپو است) |
| Build Command | `npm install --include=dev && npm run build` |
| Start Command | `npm run start` |
| Health Check Path | `/api/health` |

سپس **Environment** → افزودن متغیرها:

| Key | Value |
| --- | --- |
| `DATABASE_URL` | رشته اتصال Neon، مثلا `postgresql://user:pass@ep-xxx.neon.tech/neondb?sslmode=require` |
| `APP_SECRET` | یک رشته تصادفی طولانی |
| `NODE_VERSION` | `20.18.0` |
| `NPM_CONFIG_PRODUCTION` | `false` |

در آخر **Manual Deploy → Clear build cache & deploy**.

> نکته: `--include=dev` لازم است چون Render مقدار `NODE_ENV=production` می‌گذارد و در این حالت
> `npm install` بسته‌های toolchain (typescript و tailwind) را نصب نمی‌کند و بیلد می‌شکند.

### شبکه‌ی ایمنی (اگر باز هم Build Command را فراموش کردید)

اسکریپت `npm start` این پروژه به `scripts/start.mjs` وصل شده است: اگر پوشه‌ی `.next` موجود نباشد،
**خودش قبل از اجرای سرور یک بار `next build` می‌گیرد** و بعد روی `PORT` مربوط به Render بالا می‌آید.
پس حتی با تنظیمات ناقص هم سرویس live می‌شود (فقط اولین بوت کندتر است).

### استفاده از Blueprint

فایل `render.yaml` در ریشه‌ی پروژه همه‌ی این تنظیمات را دارد؛ کافیست در Render گزینه‌ی
**New → Blueprint** را بزنید و ریپو را انتخاب کنید، سپس فقط `DATABASE_URL` را وارد کنید.

### تشخیص سریع مشکل

آدرس `https://<your-app>.onrender.com/api/health` را باز کنید:

- `{"ok":true,"db":true}` → همه‌چیز سالم است.
- `{"ok":false,"reason":"DATABASE_URL تنظیم نشده است"}` → متغیر محیطی را اضافه کنید.
- `{"ok":false,"reason":"..."}` → متن خطا مشکل اتصال Neon (معمولاً نبودن `?sslmode=require`) را نشان می‌دهد.

## 📲 ساخت فایل APK با PWABuilder

همه پیش‌نیازها به‌صورت خودکار آماده می‌شوند:

- اسکریپت `prebuild` پیش از هر build اجرا می‌شود و آیکون‌های `96…1024` پیکسل،
  نسخه‌های `maskable` (۱۹۲ و ۵۱۲)، `apple-touch-icon` و سه اسکرین‌شات را
  از روی لوگوی SVG می‌سازد. بنابراین حتی اگر فایل‌های PNG هنگام انتقال به مخزن
  یا سرور جا بمانند، روی Render دوباره ساخته می‌شوند.
- علاوه بر آن، مسیرهای پویا (`/icons/[file]`, `/screenshots/[file]`,
  `/apple-touch-icon.png`) به‌عنوان لایه دوم محافظ، تصویر را در لحظه تولید می‌کنند
  تا هرگز خطای ۴۰۴ رخ ندهد.
- سرویس‌ورکر با یک اسکریپت درون‌خطی در `<head>` بلافاصله ثبت می‌شود تا ابزارهای
  بررسی PWA آن را تشخیص دهند.

### مراحل گرفتن APK

1. تغییرات را روی Render منتشر کنید (Build Command: `npm install --include=dev && npm run build`).
2. در [PWABuilder.com](https://www.pwabuilder.com) آدرس **صفحه اصلی** سایت را وارد کنید (نه `/login`).
3. دکمه Retest را بزنید؛ همه Action Items باید سبز شوند.
4. `Package For Stores → Android` یا `Download Test Package` را بزنید.

## 🌐 پایداری شبکه و کارکرد آفلاین (معماری)

**مشکل قبلی:** همه صفحات `force-dynamic` بودند، یعنی هر بار باز کردن هر صفحه نیاز به
پاسخ سرور داشت. روی اینترنت موبایل (و سرور رایگان Render که پس از بی‌کاری خاموش می‌شود)
این درخواست‌ها تایم‌اوت می‌کردند و برنامه بالا نمی‌آمد.

**راه‌حل اصولی:**

1. **همه صفحات استاتیک شدند** (`○ Prerendered`). پوسته برنامه دیگر هیچ وابستگی به سرور ندارد.
2. **پیش‌کش کامل** — سرویس‌ورکر (v8) در نصب اولیه هر ۳۴ مسیر برنامه را کش می‌کند.
3. **Cache-First برای صفحات** + بروزرسانی خاموش در پس‌زمینه → باز شدن آنی روی هر اینترنتی.
4. **مهلت کوتاه برای داده** (۶ ثانیه) و برگشت فوری به کش.
5. **صف آفلاین** روی IndexedDB برای همه نوشتن‌ها + همگام‌سازی خودکار.
6. **نشست محلی** (۱۴ روز) تا برنامه بدون سرور هم باز شود.
7. **`/api/ping`** فوق‌سبک (بدون دیتابیس) برای بیدار کردن سرور + پینگ هر ۴ دقیقه.

## 🔐 تایید سیم‌کارت (روش اصولی)

مرورگرها به دلایل امنیتی **اجازه خواندن شماره سیم‌کارت را نمی‌دهند**. روش استاندارد و
قابل اتکا، اثبات در دسترس بودن سیم‌کارت با **کد یکبارمصرف (OTP)** است:

1. نماینده نام کاربری/رمز را وارد می‌کند.
2. سامانه یک کد ۵ رقمی به **شماره ثبت‌شده توسط مدیر** پیامک می‌کند.
3. اگر آن سیم‌کارت داخل همان گوشی باشد، کد دریافت می‌شود → ورود انجام و **گوشی به حساب قفل می‌شود**.
4. اگر سیم‌کارت در گوشی نباشد، کدی نمی‌رسد → ورود ممکن نیست.
5. ورودهای بعدی از همان گوشی بدون کد انجام می‌شود؛ هر گوشی دیگری مسدود است.
6. مدیر می‌تواند از صفحه «کاربران» گوشی را **آزاد** کند (تعویض دستگاه).

### تنظیم سرویس پیامک
صفحه «پیام‌رسان‌ها» → بخش «سرویس پیامک»: کاوه‌نگار، SMS.ir، ملی‌پیامک یا آدرس سفارشی.
می‌توان با متغیرهای محیطی هم تنظیم کرد: `SMS_PROVIDER`, `SMS_API_KEY`, `SMS_SENDER`, `SMS_PATTERN`.

> اگر سرویس پیامک تنظیم نشده باشد، کد به‌صورت خودکار به **اعلان مدیر** ارسال می‌شود تا
> شفاهی به نماینده بدهد؛ بنابراین سامانه بدون پیامک هم کار می‌کند.

## 🔐 کنترل سیم‌کارت — چهار حالت

مدیر برای **هر کاربر جداگانه** از صفحه «کاربران» یکی از این حالت‌ها را انتخاب می‌کند:

| حالت | رفتار |

## 🛡 مقاوم‌سازی سرور در برابر قطعی شبکه

### ۱) Keep-Alive — جلوگیری از خوابیدن سرویس
دو مسیر بدون احراز هویت و بدون تماس با دیتابیس:

```
GET /ping        → 200 "OK"        (زمان پاسخ ~۶ms)
GET /ping?json   → {"status":"OK","uptimeMs":...}
GET /api/ping    → همان
HEAD /ping       → 200
```

**تنظیم UptimeRobot:** New Monitor → HTTP(s) → URL: `https://<app>.onrender.com/ping`
→ Interval: **۵ دقیقه**. با این کار سرویس رایگان Render هرگز خاموش نمی‌شود.

### ۲) Retry با Exponential Backoff + Jitter
ماژول `src/lib/retry.ts`:

| API | کاربرد |
|---|---|
| `withRetry(fn, opts)` | اجرای هر عملیات با تلاش مجدد |
| `withRetrySafe(fn, fallback)` | نسخه امن با مقدار پیش‌فرض |
| `fetchWithRetry(url, init)` | درخواست HTTP مقاوم (پیام‌رسان، پیامک، پروکسی) |
| `dbRetry(fn, label)` | کوئری دیتابیس با تلاش مجدد |
| `dbTransaction(fn)` | تراکنش با BEGIN/COMMIT/ROLLBACK و retry |

**الگوی تاخیر (Full Jitter):** `۱s → ۲s → ۴s → ۸s → ۱۶s` با سقف **۳۰ ثانیه**؛
هر مقدار به‌صورت تصادفی بین نصف تا کل مقدار نمایی انتخاب می‌شود تا رگبار همزمان ایجاد نشود.

**خطاهای قابل تکرار:** `ECONNRESET`, `ETIMEDOUT`, `ECONNREFUSED`, `EAI_AGAIN`, `EPIPE` …
کلاس‌های PostgreSQL `08xxx` (اتصال)، `53xxx` (منابع)، `57Pxx` (خاموشی)، `40001/40P01` (تداخل)،
پاسخ‌های HTTP `5xx`, `429`, `408` و پیام «endpoint is disabled» مخصوص Neon.

**خطاهای غیرقابل تکرار (فوراً پرتاب می‌شوند):** `4xx`، نقض کلید یکتا `23505`، `AbortError`.

### ۳) اتصال دیتابیس Neon
`src/db/index.ts` رشته اتصال را خودکار نرمال می‌کند:

```
ورودی : postgresql://u:p@ep-cool-fire-123.eu-central-1.aws.neon.tech/neondb
خروجی : postgresql://u:p@ep-cool-fire-123-pooler.eu-central-1.aws.neon.tech/neondb
        ?sslmode=require&connect_timeout=15&application_name=sabt-etelaat-kol
```

- تبدیل خودکار به endpoint نوع **`-pooler`** (PgBouncer)
- **`connect_timeout=15`** برای فرصت بیدار شدن دیتابیس
- `statement_timeout` و `query_timeout` برابر ۲۰ ثانیه
- `keepAlive` فعال، `max=8`, `min=0`, `idleTimeout=30s`
- شنونده `pool.on("error")` تا خطای اتصال بی‌کار فرآیند را از پا درنیاورد

`GET /api/health` وضعیت کامل را برمی‌گرداند:
`{"ok":true,"db":true,"latencyMs":8,"pooler":true,"connectTimeoutSec":15}`

## 📡 رفع «This page couldn't load» و صفحه آفلاین چسبنده

### ریشه مشکل
سرویس‌ورکر برای ناوبری **کش-اول** بود؛ روی اینترنت موبایل ایران که سرور در دسترس
نبود، نسخه کش‌شده سرو می‌شد و کاربر در صفحه آفلاین گیر می‌کرد.

### ۱) HTML هرگز کش نمی‌شود
در `next.config.ts` برای همه مسیرها:
`Cache-Control: no-cache, no-store, must-revalidate, max-age=0` + `Pragma: no-cache` + `Expires: 0`
با استثنای `/_next/static/*` که `immutable` می‌ماند (نامشان هش‌دار است).

### ۲) پیام واضح به‌جای صفحه آفلاین
کامپوننت `ConnectionStatus`: نوار پایین صفحه با پیام
**«ارتباط با سرور برقرار نیست — لطفاً اتصال اینترنت خود را بررسی کنید»**
به‌همراه دکمه‌های «بررسی مجدد»، «عیب‌یابی» و «بستن». کاربر می‌تواند کار خود را ادامه دهد.
تشخیص آفلاین با **پینگ واقعی سرور** انجام می‌شود (نه `navigator.onLine` که در ایران گمراه‌کننده است)
و فقط پس از دو شکست پیاپی هشدار می‌دهد.

### ۳) سرویس‌ورکر: ناوبری «شبکه-اول»
```js
if (req.mode === "navigate") {
  ❶ شبکه با مهلت ۵ ثانیه و cache: "no-store"
  ❷ اگر شکست خورد → همان صفحه از کش (برنامه کامل کار می‌کند)
  ❸ اگر نبود → پوسته اپ (/panel یا /) تا مسیریابی کلاینت ادامه یابد
  ❹ آخرین راه → صفحه راهنما با دکمه تلاش مجدد
}
```
درخواست‌های RSC (ناوبری داخلی Next) هم مدیریت می‌شوند تا جابه‌جایی بین صفحات آفلاین کار کند.

### ۴) کار آفلاین + ارسال دستی
- خواندن داده‌ها از کش (آخرین نسخه دریافتی).
- هر ثبت/ویرایش در **IndexedDB** صف می‌شود و پیام
  «اطلاعات ذخیره شد و پس از وصل شدن اینترنت ارسال می‌شود» نمایش داده می‌شود.
- نوار «N مورد در انتظار ارسال» با دکمه **«ارسال اکنون»** برای ارسال دستی.
- ارسال خودکار با Background Sync، بازگشت اینترنت، فوکوس صفحه و هر ۲۵ ثانیه.
- صفحه `/offline` دیگر بن‌بست نیست: هر ۸ ثانیه خودکار بررسی می‌کند و دکمه
  «ادامه در حالت آفلاین» کاربر را وارد پنل می‌کند.

| `platform` | telegram / bale / eitaa / whatsapp |
| `label` | عنوان دلخواه برای شناسایی |
| `targetType` | group / channel / phone |
| `target` | chat_id، آیدی کانال یا شماره تلفن |
| `token` | توکن ربات یا کلید API |
| `provider` | سرویس واسط واتساپ: whatsiplus / ultramsg / cloudapi / custom |
| `apiUrl` | آدرس سفارشی با `{phone}` و `{text}` و `{token}` |
| `enabled` | فعال/غیرفعال بودن این مقصد |
| `lastStatus`, `lastOkAt`, `lastErrorAt` | وضعیت آخرین ارسال برای نمایش در پنل |

جدول `message_logs` تاریخچه کامل هر ارسال (موفق/ناموفق + متن خطا) را نگه می‌دارد.

### توابع اصلی (`src/lib/messaging.ts`)
```ts
formatOrderMessage(order)      // ساخت متن سفارش
sendOne(target, text)          // ارسال به یک مقصد (مستقیم → پروکسی)
dispatchText(text, orderId?)   // ارسال به همه مقصدهای فعال
dispatchOrder(order)           // ارسال یک سفارش
fetchUpdates(platform, token)  // کشف خودکار chat_id
```

### مدیریت خطا
- هر درخواست تا **۳ بار** با فاصله ۱ → ۲ → ۴ ثانیه (Full Jitter) تکرار می‌شود.
- ارسال‌ها با `Promise.allSettled` موازی انجام می‌شوند؛ **شکست یکی بقیه را متوقف نمی‌کند**.
- اگر ارسال مستقیم شکست بخورد، خودکار از **پروکسی Cloudflare** تلاش می‌شود.
- پاسخ سرویس‌هایی که در خطا هم کد ۲۰۰ می‌دهند (مثل whatsiplus) از روی **بدنه** بررسی می‌شود.

### راهنمای دریافت توکن
| پیام‌رسان | توکن | مقصد |
|---|---|---|
| **تلگرام** | @BotFather → `/newbot` | chat_id عددی؛ گروه با `-100…` |
| **بله** | @BotFather داخل بله → `/newbot` | chat_id عددی |
| **ایتا** | ثبت‌نام در `eitaayar.ir` | آیدی کانال با `@` |
| **واتساپ** | کلید API از `whatsiplus.ir` (یا UltraMsg / Cloud API) | شماره مقصد |

برای تلگرام و بله دکمه **«🔎 دریافت خودکار chat_id»** در پنل وجود دارد: ربات را در گروه عضو
کنید، یک پیام بفرستید و دکمه را بزنید تا فهرست چت‌ها با یک کلیک انتخاب شود.
